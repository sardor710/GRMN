# Backend API and service contracts — version 1

Task 02A, 2026-11-10. Authoritative TypeScript definitions: `src/contracts/commerce.ts`, `src/contracts/pagination.ts`, `src/server/context.ts`, `src/server/service-contracts.ts`. These contracts are not implemented HTTP endpoints or authentication. Existing routes remain unchanged until their migration task.

## Boundaries and source of identity

Browser-safe contracts contain no database/environment/auth-library imports. Server-derived `Principal` and `CartActor` are separate types. HTTP handlers obtain actors from a verified session or a validated opaque guest cookie; never deserialize a submitted actor, user ID, permission array or token hash as authority. Services enforce ownership even when called directly from a Server Component. A typed object is not runtime validation: reject unknown fields and validate at the future handler/service boundary.

The seven methods in `CommerceServices` are the integration seam for Tasks 08–16. They return promises and paginated DTOs; no production implementation is supplied in Task 02. A transaction owner passes the exact `Transaction` object from `src/server/db/transaction.ts` to participating repositories, instead of each repository opening an independent connection/transaction.

## Scalars, currency and versions

| Value | Contract |
|---|---|
| Internal entity IDs | UUID strings generated by application, enforced when schemas/services arrive; legacy public keys remain distinct |
| Public product key | Preserved route key, never re-created from a mutable title |
| Money | `{ amountMinor: string, currency: "KZT" }`; unsigned canonical integer string, no exponent/floating-point JSON number; runtime checks in pricing/import tasks |
| USD equivalent | Separate `{ amountMinor, currency: "USD", exchangeRate }`; display only, never a provider/payment/refund amount |
| Exchange rate | Decimal string `kztPerUsd`, positive, at most 12 integer and 8 fractional digits; `id`, positive integer `version`, `updatedAt` snapshot; no valid rate -> `usdEquivalent: null` and show KZT |
| Date/time | ISO 8601 UTC string; no invented historical event timestamp |
| Locale | `kk`, `ru`, `en`; URL/translation/fallback strategy deferred |
| Aggregate version | Integer starting at 1; update commands use expected version, compare atomically, conflict ->409 |
| Phone | Required for new quick checkout; normalize/validate with explicit country at identity boundary; submitted phone is unverified until possession is proved |

`PriceDTO.selling` is the current customer price and `compareAt` optional reference price. Currency selection changes display only. A quote fixes KZT amounts and the shown USD rate/version independently; changing the admin rate cannot alter an existing KZT order. Tax-inclusive price policies must be normalized into explicit quote net/tax components once the owner confirms them.

## Catalog and pagination

`ProductQuery` requires market, locale, display currency. Optional filters: search (maximum 200 characters), one category key, up to 20 activity keys, documented level/case-size unions; sort allowlist `name_asc`, `price_asc`, `price_desc`, `newest`. Published-only list/detail responses expose availability, not warehouse counts, supplier cost or drafts. A minimum card price for multiple variants must represent an actual available variant, with the presentation clarified in Task 09.

`normalizePageInput` supplies defaults 24 for catalog and 20 for account/admin, and rejects noninteger/out-of-range limits (1–100) or empty/>2048-character cursors. `Page<T>` returns `items` and nullable `nextCursor`. Cursor encoding/decoding arrives with query repositories: bind version, sort tuple and filter scope; use deterministic sort+ID ordering. Cursor contents never authorize data access; customer queries still filter by the session's user ID. Empty lists remain empty.

### Admin catalog API (M2, PostgreSQL only)

Staff only. Reads need `catalog:read`. Writes need `catalog:write`, plus `inventory:write` when they create a product or change stock. Mutations must be same-origin. Query keys outside the allowlist are 400. On the legacy JSON backend every route answers 501. Response types are in `src/contracts/admin-catalog.ts`. Routing is in `src/server/cms/catalog-http.ts`, the service is `src/server/cms/catalog-service.ts`, and the command schema is `src/server/cms/product-command.ts`.

| Route | Request | Response |
|---|---|---|
| `GET /api/admin/catalog/products` | `limit` (1–100, default 50), `cursor`, `search` (name, SKU, family), `status` (`draft`/`published`/`archived`/`all`; default: not archived), `category` (key, includes descendants), `family`, `stock` (`in` = available > 0, `low` = 1–5, `out` = ≤ 0) | `{items: ProductListRow[], nextCursor, total, limit}`. Keyset order is `updated_at DESC, id DESC`, and the cursor is bound to the filters |
| `GET /api/admin/catalog/skus` | same keys | `{items: SkuRow[], …}`: one row per non-archived variant, grouped by product, SKU ascending |
| `GET /api/admin/catalog/products/:key/variants` | – | `{variants: SkuRow[]}`, which expands a grouped row |
| `GET /api/admin/catalog/products/:key` | – | `{product}`: the full editor payload. It has the legacy CMSProduct shape with stored ids, plus `categories`, `primaryCategory`, `relations`, `compatibility` {`devices`, `accessories`, `compatibleDevices`, `compatibleAccessories`}, and per-variant `stock`/`stockBaseline`/`stockReserved`/`stockAvailable` |
| `POST /api/admin/catalog/products` | product command without `id` (body ≤ 4 MB) | 201 `{product}` |
| `PUT /api/admin/catalog/products/:key` | product command with `version` | `{product}`; 409 `VERSION_CONFLICT` / `STOCK_CONFLICT` / `SKU_CONFLICT` (body also carries `conflicts: string[]`) |
| `PATCH /api/admin/catalog/variants/:variantId` | `{version (product), price?, originalPrice?, stock?, stockBaseline?, status?, imageIds?}` | `{product: {id, version}, variant: SkuRow}` |
| `GET /api/admin/catalog/taxonomy` | – | `{categories: TaxonomyNode[], epoch}` with ETag `W/"taxonomy-<epoch>"`, `private, max-age=300`, and 304 on `If-None-Match` |
| `GET /api/admin/catalog/picker` | `search`, `category`, `exclude`, `status`, `limit` (default 20), `cursor` | `{items: PickerRow[], nextCursor}`, with no total |
| `POST /api/admin/catalog/restock` | `{productId, variantId?, quantity, idempotencyKey, note?}` | the inventory adjustment result plus `product: {id, version}`; a ledger `receive`, replay-safe per key |

The older `/api/admin/products` keeps its response shapes. Its POST uses the same writer (and returns `{error, code: "SKU_CONFLICT", conflicts}` on a SKU clash). Its PATCH changes only the named SEO fields.

## Profile, address and wishlist

Quick checkout: name, phone, delivery address; email optional. Full signup/profile completion: name, email, phone. Subsequent phone login proves possession. Do not create a fake customer email or attach old orders based only on a typed phone/email. `CompleteProfileCommand.phone` must match the verified identity; changing it requires a separately verified change flow.

`DeliveryAddress` requires recipientName/phone/countryCode/city/line1, with optional line2/region/postalCode; future validators impose length bounds and market-specific required fields. An address selection is either inline structured data or a saved address ID plus version; saved address ownership is always checked. Maximum five saved addresses; primary selection serialized per user in Task 10.

Wishlist belongs to the authenticated user, uses persistent unique product membership, and returns safe public product cards. Archived/missing items require an explicit unavailable presentation or removal policy in Task 20; never expose drafts to fill a wishlist item.

## Cart, quote and checkout

- Cart changes accept variant ID, positive quantity up to 99 and expected cart version; maximum 100 distinct lines. Browser price/name/stock/discount claims are ignored. An empty/removed line is handled by the future remove operation rather than a negative quantity.
- `QuoteCommand` binds cart version, delivery selection, display currency and optional coupon. `CheckoutQuoteDTO` binds cart ID/version, line allocations, KZT subtotal/discount/shipping/tax/total, policy versions and expiry. Grand total = subtotal − discount + shipping + tax; normalize any tax-inclusive price to the required components before applying this equation. Snapshot rounding allocations; pricing implementation is Task 13.
- `CheckoutCommand` contains quote ID, cart version, required quick-contact name/phone, delivery selection and payment-method code. The server rechecks that contact/address agree with the accepted quote; changed delivery/contact inputs require revalidation/requote where they affect price, tax, eligibility or identity. No total/currency/user ID in the command.
- An `Idempotency-Key` header (16–128 printable ASCII characters) is required for checkout. Scope it to verified user/guest capability and operation; different request under one key ->409, same request returns the same order. Hash the canonical accepted payload; never print raw customer data in diagnostics. Retention depends on provider retry policy in Task 15.
- Defined method codes: `demo`, `kaspi`, `secondary`. Only explicitly enabled methods can be selected; `kaspi`/`secondary` are disabled until later integration. No manual-payment launch policy has been assumed.
- `CheckoutResultDTO.paymentMode` distinguishes demo/live; `simulated` is not a capture and must never produce a paid money ledger entry. A timeout may return the original pending order with `retry_required`; the browser return URL never marks paid.
- Guest order access uses a separate secure capability, minted server-side and delivered with an appropriate HttpOnly cookie. The cookie hash is not a JSON DTO field; repeating a request must not grant access outside the same actor scope. Concrete cookie route/path/expiry and replay semantics are Task 14 security design.

## Orders and staff mutations

Payment, fulfillment and order statuses are separate unions. `OrderDetailDTO` contains customer-visible purchase snapshots and approved events only: no carrier/tracking/back-office notes, coordinates, admin identity or provider payload. Legacy unstructured addresses have an explicit discriminated representation; missing historical SKU/phone can be null and `dataQuality` marks incomplete legacy data. Never invent values to satisfy a type. Unresolved currency rows are not served as KZT without import reconciliation.

`OrderTransitionCommand` allows the specific high-level actions `start_processing`, `request_cancellation`, `cancel`, `close`, with expected version/reason. It cannot directly set payment status, role or stock. Shipping/refund orchestration has its own later service interface and permission checks. Input transition validity remains a server policy; having a union value does not make a transition valid.

## HTTP error mapping

All errors use `ApiErrorResponse`: `{ error: { code, message, fieldErrors?, requestId } }`. Messages are safe public explanations; request IDs connect to redacted server diagnostics. Never expose SQL, credentials, sessions, OTP, internal notes or provider secrets.

| Status | Code(s) |
|---|---|
| 400 | INVALID_INPUT (including unknown fields or invalid pagination) |
| 401 | UNAUTHENTICATED |
| 403 | FORBIDDEN for staff permissions |
| 404 | NOT_FOUND, including another customer's resource |
| 409 | VERSION_CONFLICT, IDEMPOTENCY_CONFLICT, OUT_OF_STOCK, QUOTE_EXPIRED, QUOTE_CHANGED |
| 422 | RATE_UNAVAILABLE or METHOD_UNAVAILABLE when requested behavior is disabled |
| 429 | RATE_LIMITED; Retry-After where meaningful |
| 503 | DEPENDENCY_UNAVAILABLE; retry only when safe |
| 500 | INTERNAL_ERROR, with no underlying error details |

Public catalog can fall back to KZT display when a USD rate is unavailable. It must never fall back to seed customer/order data or return a successful mutation after DB failure. Private responses use no-store; public cache keys include market, locale, display currency and FX version.
