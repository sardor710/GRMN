### Changed

- `src/server/account/service.ts`:
  - **`approveLegacyClaim(headers, {orderId, expectedVersion, reason, phoneNumber?})`**
    - Needs `customers:write` with fresh staff MFA (15 minutes) through the new `authorizeFresh` option. Without that option it fails closed with 403.
    - Locks the order. The order must be unowned and at the expected version (otherwise 409), and the phone must be E.164 (otherwise 400). The phone defaults to the order's contact phone; staff may supply a confirmed one instead.
    - Revokes any open receipt for the order and issues a 32-byte base64url receipt that expires after 72 hours.
    - Audits `staff.legacy_claim_approved` with the approval ID, an HMAC digest of the phone (never the raw phone), whether the phone was overridden, and the reason.
  - **`claimLegacyOrder(headers, {orderId, receiptToken, challengeId, code})`**
    - Staff accounts are refused (403); this is separation of duties.
    - Needs a verified owner phone and a fresh `order_claim` OTP for that phone.
    - Lock order: user, then order (unowned), then approval (by hash, order, phone, open and unexpired). Every mismatch returns the same 404.
    - Sets `orders.user_id` and bumps the version, consumes the receipt, and audits `customer.legacy_order_claimed`.
  - **`changePhone(headers, {phoneNumber, currentChallengeId, currentCode, challengeId, code, expectedVersion})`**
    - Staff accounts are refused (403). A verified current phone is required, and the new number must be different.
    - Consumes a `phone_change_current` proof for the current number and a `phone_change_new` proof for the new one.
    - Then: owner lock, profile CAS (version 0 when there is no profile), and the unique `users.phone_number` (otherwise 409).
    - Updates the profile phone and revokes pending completion sessions for the new number.
    - **Deletes every session of the user** and audits `customer.phone_changed`. Returns `{phone, version, signedOut: true}`.

- `src/server/auth/factory.ts`:

  - After creating a phone sign-in session, it re-checks that the proved phone still belongs to that user. If not, it deletes the session and returns 401 (review I1).

  - Who may call it: no session gets 401; a non-staff account gets 403 (customers own no password); staff without MFA admission get 403.
  - A budget of 5 attempts per 15 minutes per user.
  - Calls Better Auth `changePassword` and audits `auth.password_changed`. If that audit write fails, the response is a visible 503.
  - The success response is `{success:true, mfaRequired:true}`.

## Review

A read-only identity-access-engineer reviewed the changed files.
- **No Critical findings.** It confirmed that receipts are hash-looked-up, consumed once, and checked against order and phone with the order locked; that every mismatch returns the same 404; that origin checks are present; and that there is no deadlock cycle (claim: users → orders → approvals; approve: orders → approvals; phone change: users → profiles).
- **Three Important findings, all fixed test-first in one pass:**
  - **I1 — the sign-in race.** `/grmn/phone/verify` could create a session after `changePhone` had deleted all sessions, so the old number kept an 8-hour session on the moved account.
    - Fix: a re-check after session creation that deletes the session and returns 401.
    - Test: "review I1…" holds an uncommitted phone change, which blocks the session insert through its foreign-key lock; it commits, and then asserts 401 with no session row. RED 200 → GREEN 401.
  - **I2 — OTP purpose.** A sign-in code was accepted for phone change and for claims.
    - Fix: `phone_challenges.purpose`, purpose-specific consume, and the purpose passed to the sender for distinct SMS text.
    - Test: "review I2…" — a sign-in code returns 401 for a claim and for a phone change, and a claim code returns 401 at sign-in.
  - **I3 — approval strength.** Approvals did not need fresh MFA, the audit row was thin, and staff could redeem receipts.
    - Fix: `requireFreshPermission` (15 minutes); the audit row carries the approval ID, phone digest and reason; claims refuse staff, folding in the reviewer's M7 (approvers are staff).
    - Test: "review I3…" — a stale grant gets 403, the audit row's contents are checked, and staff self-redemption gets 403.

## Rulings

Each ruling below has the cost if it is wrong.
1. **Split 10B into 10B (server and HTTP) and 10C (AccountDashboard UI).**
   - One reviewable security slice per session. The UI still needs `src/app/account/page.tsx` and its unit test (which forbids importing `AccountDashboard`) to be reworked.
   - Cost: one extra session.
2. **Customer recovery is phone possession,** via the existing `/grmn/phone/verify` sign-in.
   - Lost or recycled-number recovery stays open as owner decision **O04**. It needs a policy and an OTP provider, so it was not invented here.
   - Cost: a customer who loses their number cannot recover the account until O04 is decided.
3. **Credential change is staff only.** Customers sign in by phone and own no password, so the UI's "Reset password" must become a phone-verification and recovery flow in 10C, never a fake success.
   - Cost: none for customers. Staff must sign in again afterwards (ruling 4).
4. **A password change revokes every session, including the current one** (`revokeOtherSessions` is forced to `true`). Better Auth issues a new session with no MFA grant, so staff must sign out and complete password + MFA again.
   - Cost: the response says `mfaRequired:true`, but the new session gets `MFA_RESTART_REQUIRED` at verify (reviewer M4). The UI must send staff to sign-in.
5. **Any unowned order can be approved, not only `legacy_incomplete` ones.** D06 says guest orders should become claimable after phone verification, and the staff approval with fresh MFA, audit and phone binding is the gate.
   - Cost: an insider with fresh MFA can still mis-assign an order. Dual approval for phone overrides is deferred (see the minors).
6. **Staff may supply `phoneNumber` when the order's contact phone is not canonical**, for example a typed legacy "8 701 …". The override is recorded in the audit row.
   - Cost: as in ruling 5.
7. **Receipts last 72 hours**, are single-use, and are superseded by a newer approval. Delivery to the customer is out of band (staff hand it over). No admin UI was built; it belongs to Task 18/19 admin work or 10C.
   - Cost: staff need the API until a UI exists.
8. **OTPs are consumed before the version and uniqueness checks.** A 409 therefore burns both codes (reviewer M5).
   - Cost: the user re-requests codes; budgets allow 5 sends per 15 minutes per number.
9. **The 409 "linked to another account" message on phone change is kept.** Only someone holding that number sees it, and they could sign in to it anyway (reviewer M6). Fold it into the O04 policy.
10. **Proof purpose is chosen by the requester.** Anyone may request a non-sign-in code. The protection is that the code only works for its purpose and the SMS text names that purpose. The OTP provider must implement purpose-specific templates when O04 and the provider are chosen.
    - Cost: if the provider sends one generic text, I2 is only partly mitigated.
11. **`account-claims.test.mjs` replaces the draft:**
    - The draft's single password-change test is expanded.
    - The phone-recovery test passed before any 10B code existed, because it guards the existing 05A flow; it is kept as a regression guard.
    - The draft's `order()` fixture became `legacyOrder()`, which inserts the order and its snapshot child in one transaction.

## Deferred minors (not fixed)

- **M1 — receipt not tied to the order version.** If the order's contact data changes after approval, the old receipt still redeems. Store `order_version` on the approval.
- **M2 — missing audit rows.** Failed claim attempts after a valid OTP are not audited, and neither is the revocation of a superseded receipt.
- **M3 — re-claim key.** The claim audit dedupe key `legacy-order-claimed:<orderId>` would make a re-claim fail with 503 if an admin un-assigned the order. No un-assign flow exists.
- **M4 — password change:**
  - MFA admission need not be fresh.
  - Failed attempts are not audited.
  - `mfaRequired:true` is misleading (ruling 4).
- **M5/M6** — see rulings 8 and 9.
- **Dual approval** when staff override the phone (reviewer I3 suggestion). Owner policy.
- **Test gaps the reviewer named.** In each case below, a protection could be removed and the current tests would still pass:
  - Receipt expiry.
  - The phone re-check races inside claim and `changePhone`.
  - Revoking completion sessions on phone change.
  - The password-change budget, and the MFA-admission check for password change (the test staff session always has a grant).
  - Revocation of a second session on phone change.
  - Cross-site origin on `/api/account/phone` and `/api/account/claims`.
  - Staff holding MFA but not `customers:write`.
- **From 10A, still open:**
  - M2 lock-order note: new writers must lock the owning `users` row first. Claim does this.
  - M5 pool pressure.
  - M7 error wording.
- **Declined to judge:**
  - Better Auth's internal `changePassword` session handling (behaviour verified by test only).
  - Order triggers locking `users` (none were found to).
  - SMS provider rate limits.
  - The admin receipt hand-over UI.
