# Garmin.kz project audit

**Audit date:** 9 November 2026 (Asia/Tashkent)  
**Scope:** local checkout at `D:\projects\garmin\GRMN`; read-only source review and safe existing checks. No production service, payment, email, deployment, or real customer journey was exercised. Line references are to the inspected working tree, which already contained uncommitted work. **Readiness verdict: demonstration storefront, not ready to accept real orders or expose the admin/API surface publicly.**

## Executive assessment

The Next.js site has a substantial Garmin-like visual shell, browsable watch catalogue and detail pages, browser cart, blog, and a CMS-style admin interface. Its commerce flow stops at a demo button: no customer form, server-created order, stock reservation, payment, or confirmation exists. More urgently, the admin data APIs have no authentication or role checks, the account orders endpoint discloses orders by arbitrary email or with no email, and the admin login uses a readable/forgeable session format and seeded demo credentials. These are launch blockers even for a catalogue-only public release unless the affected routes are removed or secured first.

The project is still US/Singapore-oriented: USD prices and a fixed US-style tax in the cart, Singapore defaults in the data store, no KZT in settings, English-only UI, and Garmin.com canonical/structured-data URLs. Payment and email gateway switches are UI data, not integrations. The JSON-file CMS is unsuitable as the authoritative production order/customer store. The successful build and small unit test suite establish that the project compiles; they do **not** validate business correctness or security.

## Detailed findings

Effort is a **rough engineering estimate**, assuming one developer familiar with the code; it excludes provider onboarding, content translation, legal review, and merchant approval. Reproduction steps below are code-level or local-only; no sensitive endpoint was invoked against a deployed service.

### Security, privacy, and storage

**S01 — Admin data APIs accept unauthenticated reads and writes. Critical · Confirmed defect.** `src/app/api/admin/orders/route.ts:4-20`, `src/app/api/admin/admins/route.ts:4-45`, `src/app/api/admin/products/route.ts:4-39`, and `src/app/api/admin/settings/route.ts:4-19` directly call store functions; the other admin CRUD route files follow the same pattern. `src/app/admin/layout.tsx:11-31` passes optional user display data but does not reject requests. **Reproduce safely:** inspect any admin route handler and find no `getCurrentAdmin`/role check; `/auth/me` alone does check (`src/app/api/admin/auth/me/route.ts:4-8`). **Impact:** anyone reaching these routes can read customer/order/admin records and change orders, users, prices, products, or settings. **Fix:** block the admin surface from public exposure immediately; require server-side authenticated sessions and per-action roles in every handler, with deny-by-default integration tests. **Estimate:** 2–5 days; depends on S02 and an identity/role design.

**S02 — Admin authentication is demo-grade and forgeable. Critical · Confirmed defect.** `src/lib/cms/auth.ts:16-45` decodes an unsigned base64 JSON cookie and trusts its email; `src/app/api/admin/auth/login/route.ts:34-44` compares plaintext passwords and even accepts an admin with no password. The login page pre-fills and displays demo credentials (`src/app/admin/login/page.tsx:10-11,45-49,91-112`), while the tracked seed/data file holds credentials (`src/lib/cms/seed.ts:26-53`, `src/lib/cms/data.json:1-25`). **Reproduce safely:** inspect `createSessionToken`: no MAC/signature or server session lookup. **Impact:** easy admin impersonation if handlers are protected only with this cookie; credential reuse and source disclosure. **Fix:** replace demo users, store one-way password hashes or use a managed identity service, use signed server sessions with expiration/rotation, remove credential hints, add login throttling and audit trails, and rotate all demo credentials before deployment. **Estimate:** 3–7 days; depends on chosen identity service.

**S03 — Account order endpoint discloses all orders or any email's orders. Critical · Confirmed defect.** `src/app/api/account/orders/route.ts:4-16` returns `getOrders()` when `email` is absent and filters only by a user-supplied email otherwise. No customer session is checked. The browser sends the editable demo profile email (`src/components/AccountDashboard.tsx:264-279`). **Reproduce safely:** read the endpoint's no-email branch; no live request was made. **Impact:** order names, contact and shipping details can be exposed. **Fix:** immediately disable this endpoint until it can derive a verified customer ID from a session and return only that customer's redacted records; test anonymous and cross-account access. **Estimate:** 1–3 days to block, 3–6 days to implement; depends on customer identity and durable order storage.

**S04 — JSON-file CMS is an unsafe production source of truth. High · Confirmed defect.** `src/lib/cms/store.ts:17-57` synchronously reads and rewrites the whole `data.json`; write errors are logged and swallowed. `saveOrder` uses timestamp/random IDs and a read-modify-write array (`src/lib/cms/store.ts:382-421`). `docker-compose.yml:1-52` has no database or data volume; standalone deployments can have multiple isolated/ephemeral instances. **Impact:** lost updates, duplicate IDs, lost orders after redeploy/restart, and falsely successful API responses when persistence fails. **Fix:** migrate orders, customers, products, users, settings, and activity to a transactional database with migrations, uniqueness constraints, backups and restore drills; fail requests on persistence errors. Keep committed sample data out of production and review its provenance. **Estimate:** 1–3 weeks; depends on database/hosting choice and data migration.

**S05 — Client input can set financial and lifecycle fields. Critical · Confirmed defect.** `src/app/api/admin/orders/route.ts:11-19` validates only presence of `clientName` and `total`, then forwards the body; `src/lib/cms/store.ts:382-415` merges arbitrary updates, accepts totals/statuses and defaults new payment status to `paid`. The same broad-body pattern exists in product/settings admin routes. **Impact:** forged paid orders, price/status corruption, invalid records, and difficult reconciliation. **Fix:** typed, schema-validated action-specific commands; calculate totals from trusted product/variant records; restrict status transitions and payment state to verified provider events; use transactions and idempotency keys. **Estimate:** 5–10 days after S01/S04 and checkout model.

**S06 — CMS content and JSON-LD need output sanitization. High · Risk.** Product/blog fields enter raw JSON in `<script>` via `dangerouslySetInnerHTML` (`src/components/seo/JsonLd.tsx:45,85,109`); `JSON.stringify` alone does not escape `<`/script terminators. Combined with unguarded admin write APIs this is a potential stored injection route. Static imported HTML in `src/components/fenix-8/Fenix8Client.tsx:12,393` is also rendered raw, but is repository-controlled, so its risk differs. **Impact:** script injection on public pages if hostile CMS data reaches schema fields. **Fix:** escape `<`, `>`, `&`, U+2028/U+2029 in JSON-LD, validate CMS inputs, add a restrictive CSP where compatible, and test malicious values. **Estimate:** 1–2 days; depends on S01.

### Commerce and operational flow

**C01 — Checkout is a misleading demo action. Critical · Confirmed defect.** `src/components/CartView.tsx:14-26,148-156` sets `placed=true` and clears items without collecting customer details or calling a server; the page itself says no payment was processed. **Reproduce:** add any product, open `/cart`, select Checkout. **Impact:** shoppers see “Thank you for your order” while the business has no order or way to fulfill it. **Fix:** until a real checkout exists, remove the order-success claim or keep the site explicitly catalogue-only; implement server order creation, shipping/contact capture, payment, confirmation, and retry-safe failure handling before commerce launch. **Estimate:** 1–2 weeks after S04/S05, excluding provider onboarding.

**C02 — Price, stock, variant and promotion logic are disconnected. High · Confirmed defect.** `ProductTop.handleAdd` sends the detail price and product ID regardless of selected case size/version/color (`src/components/ProductTop.tsx:18-29,103-159`); generic details invent three case sizes (`src/lib/products.ts:313-329`). Cart trusts stored prices and quantities (`src/lib/cart.tsx:27-69`). `stock` exists in CMS (`src/lib/cms/store.ts:164-190`) and discounts have CRUD (`:226-275`), but purchase does not check stock, apply discounts, or decrement/reserve inventory. Product page even promises shipment unconditionally (`src/components/ProductTop.tsx:150`). **Impact:** wrong SKU/price, overselling, unhonored coupons. **Fix:** model sellable variants/SKUs and stock, bind selector to SKU/image/price/availability, submit IDs/quantity only, quote on server, reserve or validate stock at order/payment boundaries, and apply eligible discounts server-side. **Estimate:** 1–2 weeks; depends on catalogue and fulfillment rules.

**C03 — Currency, taxes, shipping and business settings conflict. High · Confirmed defect.** Cart formats `$`/`en-US`, uses free shipping for every nonempty cart, and charges 7.25% (`src/components/CartView.tsx:9-17,121-160`). Product cards and buy box say USD (`src/components/ProductCard.tsx:43-46`, `src/components/ProductTop.tsx:103`). Admin settings offer SGD/USD/EUR/GBP, not KZT (`src/app/admin/settings/page.tsx:181-196`), and `getSettings()` is only read by its API (`src/app/api/admin/settings/route.ts:4-5`). **Impact:** inaccurate Kazakhstani checkout totals and misleading pricing. **Fix:** agree KZT pricing and tax treatment with finance/legal; maintain one server-side price/tax/shipping quote and KZT formatter, expose a consistent display quote, and test regional delivery fees. **Estimate:** 4–8 days after business rules and S04.

**C04 — Order tracking fabricates milestones and payment verification wording. High · Confirmed defect.** `src/lib/cms/order-lifecycle.ts:76-152` synthesizes milestone times from fixed offsets and labels creation “payment verified”; `src/lib/cms/store.ts:369-379` inserts them on read. `saveOrder` defaults new orders to `paid` and `processing` (`:404-405`). **Impact:** customers/admin may believe nonexistent payment and shipment events occurred. **Fix:** record actual append-only payment and fulfillment events from verified sources, display pending states honestly, and show estimated dates separately from completed events. **Estimate:** 4–8 days; depends on order/payment/shipping integrations.

**C05 — Customer account is an editable demo, not an account. High · Confirmed defect.** `/account` renders `initialProfile`, `initialAddresses`, and example paid orders (`src/components/AccountDashboard.tsx:45-81,81-181,221-247`); edits only call React state setters (`:312-327,402-432`). If API returns no orders, example orders remain (`:271-277`). Password recovery shows a sent-message after a timeout, without a request (`:330-343`). **Impact:** false order history and recovery claims; lost profile edits on refresh; users cannot reliably track orders. **Fix:** remove demo data and success claims from public account UI; add real customer authentication, verified profile/address persistence, secure reset tokens and actual order linkage. **Estimate:** 1–2 weeks; depends on S03/S04 and email provider.

### Payments

**P01 — No commerce payment integration exists. Critical · Confirmed defect.** There is no checkout/payment route in `src/app/api`; `CartView` is a local demo (`src/components/CartView.tsx:14-26,148-156`). `stripeEnabled` and `garminPaySandbox` are settings fields/UI toggles (`src/lib/cms/types.ts:244-251`, `src/app/admin/settings/page.tsx:226-255`), with no initiating call. The Garmin Pay *watch feature* minisite is unrelated to merchant checkout. **Impact:** no authorized KZT payment, no trustworthy paid status or refund path. **Fix:** select a contracted KZT-capable merchant provider, integrate hosted payment initiation using a server-calculated order amount, signed callback verification, idempotent finalization, and authoritative status polling/reconciliation. Implement cancellation, failed/abandoned payment expiration, and refund controls before enabling those operations in admin. **Estimate:** 1–3 weeks engineering plus merchant onboarding; depends on provider, settlement, refund policy and credentials.

**P02 — Payment state has no reconciliation or guarded transitions. Critical · Confirmed defect.** Order status can be set directly through the admin API and new orders default to paid (`src/app/api/admin/orders/route.ts:9-19`, `src/lib/cms/store.ts:382-421`); no payment ID, callback event ledger, or retry/idempotency mechanism is visible in the order type (`src/lib/cms/types.ts:211-240`). **Impact:** duplicate processing, “paid” without settled funds, and no reliable recovery after callback loss. **Fix:** separate `Order` and `PaymentAttempt`, store provider IDs and immutable event IDs, validate amount/currency/order on signed callbacks, make transitions idempotent in a transaction, poll pending attempts and reconcile daily, and gate fulfillment on verified payment. **Estimate:** 5–10 days in addition to P01; depends on S04/S05.

**Provider reality check (official documentation, checked 9 November 2026):** Halyk ePay's [widget documentation](https://epayment.kz/docs/platezhnyi-vidzhet) describes KZT, `rus/kaz/eng` language values, and payment notification links; its [status documentation](https://epayment.kz/docs/check-status-payment) describes server status lookup. Freedom Pay's [merchant overview](https://docs.freedompay.kz/doc-741636) describes a hosted payment page and KZT examples; its [callback guidance](https://docs.freedompay.kz/overview-2504969m0) requires signature, order/amount/currency checks, duplicate processing protection and status lookup if callbacks are missed; [refund documentation](https://docs.freedompay.kz/11621013e0) covers full/partial refund operations. These demonstrate **possible integration patterns**, not an approved provider, merchant eligibility, available methods for this business, pricing, settlement terms, or live credentials. Decide with the merchant and provider; do not infer that the existing Stripe toggle is usable in Kazakhstan.

### Email and communications

**E01 — Marketing subscription and password recovery claim delivery without sending anything. High · Confirmed defect.** `src/components/NewsletterSignup.tsx:54-61` only sets local `submitted`; `src/components/AccountDashboard.tsx:330-343` announces a reset link after `setTimeout`. `EmailSignup` merely navigates to `/newsletter` (`src/components/EmailSignup.tsx:15-24`). **Impact:** lost leads and customers waiting for nonexistent mail. **Fix:** suppress success messages until server acceptance; build consent capture/unsubscribe persistence for marketing and a real tokenized recovery flow if accounts are launched. **Estimate:** 2–5 days after provider and identity choice.

**E02 — Transactional message pipeline is absent. High · Confirmed defect.** No mail SDK in root `package.json:31-58`, no mail route/job in `src/app/api`, and checkout never creates an order. Order creation/payment/failure/shipping and account events therefore trigger no email. **Impact:** customers lack receipts and status updates; support has no delivery evidence. **Fix:** define event-driven, localized templates for order received, payment success/failure, shipment, refund, verification/recovery as applicable; send from an idempotent outbox/queue with retries, provider delivery webhooks, suppression handling, operator alerts, and a verified sender domain (SPF/DKIM/DMARC). Show a durable on-site confirmation even if email fails. **Estimate:** 1–2 weeks; depends on provider, S04, P01, localization and domain ownership.

### Localization, content, experience and accessibility

**L01 — No locale system for Kazakh or Russian. High · Confirmed defect.** `src/app/layout.tsx:36-42` fixes `lang="en"`; no `[locale]` route or translation catalogue is present in `src/app`/`src/lib`. Hardcoded English appears across checkout, admin, product, error and account UI (`src/components/CartView.tsx:20-160`, `src/components/AccountDashboard.tsx:312-343`). Dates/currency use `en-US` (`src/lib/cms/order-lifecycle.ts:160-173`, `src/components/ProductCard.tsx:43`). **Impact:** poor comprehension, inaccessible validation/communications for target audiences, and no multilingual indexing. **Fix:** decide locales and default; add locale-aware routes/switcher/persistence/fallback, translated UI and catalog content, localized validation/notifications/templates, `Intl` KZT/date formatting, `html lang`, canonical/hreflang/sitemap variants. Audit each route/locale for untranslated strings. **Estimate:** 2–4 weeks engineering/content coordination; translation volume is separate.

**L02 — Kazakhstan operational information is mostly placeholder or foreign-market copy. High · Confirmed defect.** `src/lib/content.ts:303-361` points shipping/returns, contact, warranty, privacy and terms links to `#`; `src/components/ProductTop.tsx:105-111` displays US financing and HSA/FSA copy; `src/lib/cms/store.ts:399-412` defaults orders to Singapore contact/address/carrier/coordinates. **Impact:** misleading promises, no clear delivery/support path, and weak buyer trust. **Fix:** owner supplies verified local legal entity/contact, delivery areas/fees/lead times, returns/warranty and privacy text; replace or remove US-only offers, connect real support/order-policy pages. Obtain qualified legal review for required disclosures and personal-data handling; this audit makes no legal determination. **Estimate:** 3–7 days implementation plus owner/legal/content decisions.

**D01 — Search, navigation and several calls to action are dead ends. Medium · Confirmed defect.** Header search has no handler (`src/components/SiteHeader.tsx:90-92`); `Support` links to `#` (`:83-89`); many top navigation, category and footer links do the same (`src/lib/content.ts:21-123,291-361`). The product `Customize` button has no handler (`src/components/ProductTop.tsx:159`). Only two category definitions resolve (`src/lib/products.ts:47-71`). **Reproduce:** click these controls in a local build; `#` leaves the user on the page. **Impact:** broken product discovery/support and false affordances. **Fix:** prioritize working search/catalogue routes and local help pages; remove or disable unsupported destinations; maintain a link inventory test. **Estimate:** 3–8 days depending on content scope.

**D02 — Navigation and modal accessibility need interaction testing. Medium · Risk.** Desktop mega-menu is opened by mouse enter only (`src/components/SiteHeader.tsx:29-53`), with no keyboard-open state or `aria-expanded`; mobile hamburger lacks expanded/controls state (`:102-116`) and mobile submenu content is not exposed (`:115-132`). Order modal declares `role="dialog"` (`src/components/OrderDetailsModal.tsx:90-92`), but a full focus/escape/return-focus audit was not performed. **Impact:** keyboard and screen-reader users may not reach catalogue links or manage overlays. **Fix:** make menu buttons keyboard-operable with focus management, expose mobile submenus, add ARIA state, and run keyboard/screen-reader tests on forms, filters, cart and modals. **Estimate:** 2–5 days; depends on final navigation structure.

**D03 — Visual fidelity is unverified; responsive risk is visible in code. Medium · Unverified.** There is no relevant Garmin reference screenshot in `docs/design-references`; `comparison.png` depicts another site. The admin shell uses a fixed `pl-64` content offset (`src/components/admin/AdminLayoutShell.tsx:25-31`), and several minisites ship large video/raw-image surfaces. **Impact:** potential clipped admin UI and inconsistent mobile rendering, but no pixel-level defect is claimed without viewport screenshots. **Fix:** capture current Garmin.kz target or approved design at mobile/tablet/desktop sizes and compare local render for navigation, typography, gallery, overlays, checkout, and admin; fix measured differences. **Estimate:** 2–5 days initial QA plus remediation.

### SEO, maintainability, performance and reliability

**M01 — Multiple inconsistent catalog/content sources. High · Confirmed defect.** `src/lib/products.ts:12-29,75-100,288-360` mixes static products, CMS products, invented fallback details and special fēnix data. The catalogue exposes every CMS product without a published/stock filter (`:75-100`), while sitemap filters published products (`src/app/sitemap.ts:78-86`); product route uses `getProductDetail` without checking status (`src/app/p/[id]/page.tsx:75-82`). Blog listing reads static `blogPosts` (`src/components/BlogExplorer.tsx:6-19`), while CMS blog API/article route may read CMS content (`src/app/blog/[slug]/page.tsx:20-27,80-82`). **Impact:** draft/unavailable pages can be sold or shown, CMS updates may not appear in listings, and page/detail/SEO can disagree. **Fix:** designate one published catalogue and blog source with typed read models and status rules; make listing/detail/sitemap/JSON-LD use the same records and cache invalidation. **Estimate:** 4–8 days; depends on S04.

**M02 — CMS API contracts and errors are weak. Medium · Confirmed defect.** Admin routes cast arbitrary JSON into broad `save*` functions (`src/app/api/admin/products/route.ts:9-29`, `src/app/api/admin/orders/route.ts:9-19`); store uses permissive partial merges and silently falls back to in-memory data on read/write errors (`src/lib/cms/store.ts:20-57`). `src/app/admin/orders/page.tsx:89-124` calls these routes from client state. **Impact:** malformed data, silent persistence failures, inconsistent UI, and hard-to-debug production incidents. **Fix:** request/response schemas, service layer, explicit error codes, transactional repository and targeted tests; keep UI components out of persistence rules. **Estimate:** 4–7 days after S04.

**M03 — Canonicals, structured data and sitemap target Garmin.com or nonexistent routes. High · Confirmed defect.** Product/blog metadata and breadcrumbs hardcode `https://www.garmin.com` (`src/app/p/[id]/page.tsx:38-63,105-115`, `src/app/blog/[slug]/page.tsx:39-64,102-122`); JSON-LD uses Garmin.com and USD plus a fixed aggregate rating (`src/components/seo/JsonLd.tsx:12-42`). Sitemap/robots fall back to Garmin.com (`src/app/sitemap.ts:7`, `src/app/robots.ts:4`) and sitemap advertises five `/c/*` categories even though only two resolve (`src/app/sitemap.ts:54-71`, `src/lib/products.ts:47-71`). Build warns `metadataBase` is absent (`src/app/layout.tsx:16-28`). **Impact:** wrong canonical/index targets, inaccurate rich results, and avoidable 404s. **Fix:** centralize a configured garmin.kz origin, add `metadataBase`, generate URLs from active routes, use actual KZT/availability/reviews, set localized alternates, and verify sitemap URLs return 200. **Estimate:** 2–5 days after route/locale decisions.

**M04 — Heavy media and the global cart provider need measurement. Medium · Risk.** `public/` has 396 files totaling ~72.4 MB (local file inventory); largest individual videos are ~1.3–3.7 MB. Some minisite videos use `preload="auto"` (`src/components/marq/MarqFireDamascusMerged.tsx:97-102`, `src/components/marq/MarqLifestyleCarousel.tsx:206-214`); lint reports multiple raw `<img>` elements. Root `CartProvider` wraps every page (`src/app/layout.tsx:42`). **Impact:** possible mobile bandwidth/LCP and JS costs; no real performance metric was measured. **Fix:** measure LCP/INP/CLS and transferred bytes per key viewport, then compress/select poster images, lazy-load below-fold video, use responsive images and reduce unnecessary client code. **Estimate:** 3–7 days after profiling.

**M05 — Monitoring, recovery and tests do not protect the business path. High · Risk.** Compose probes only the homepage (`docker-compose.yml:18-25`), while store write errors are swallowed (`src/lib/cms/store.ts:40-57`). Tests cover helper logic, not authorization, checkout, payment or email. No backup/restore, structured event logging, alerting or reconciliation job was observed in the Next code/config. **Impact:** data loss or failed orders could go undetected. **Fix:** health/readiness checks for database and queue, correlated order/payment logs without PII, alert on failed callbacks/mail/stock reconciliation, backups and restore exercise, and end-to-end tests for checkout and access control. **Estimate:** 1–2 weeks staged alongside S04/P01; external platform controls unverified.
